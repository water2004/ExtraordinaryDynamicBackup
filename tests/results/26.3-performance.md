# Minecraft 26.3：备份与恢复等待优化

日期：2026-10-27。基线 `ab2d92d`，优化与调度回归测试 `67a3b24`。

## 同场景专用服对照

Windows x64，Microsoft OpenJDK 25.0.2，Fabric Loader 0.19.5，Fabric API 0.162.0+26.3。两次运行使用同一机器、相同测试代码生成的数据结构、相同依赖组合与配置，每次新建独立测试世界。启用 10 秒 watchdog，C2ME `gcFreeChunkSerializer=true`。没有关闭 watchdog，也没有修改备份格式、批次上限或写入完成条件。

组合为当时 `compatibility-lock.json` 的全部 30 项依赖（排除 Async），包含 Carpet/additions、C2ME、Lithium、VMP、ECO、ServerCore、Servux、地图和语音等；完整列表见两个 profile 文件。该轮 ECO 为 alpha.11，版本与文件哈希以 [`e8f6af1` 的 lock 文件](https://github.com/water2004/ExtraordinaryDynamicBackup/blob/e8f6af1/tests/compatibility-lock.json) 为准；后续更新当前 lock 不改变本报告的历史结果。ECO 与 Async 没有合装。

| --- | ---: | ---: | ---: |
| 256 个已加载区块、1,024 个实体：备份，5 轮平均 | 1,060.6 ms | 563.0 ms | 46.9% |
| 同场景恢复，5 轮平均 | 3,312.8 ms | 429.2 ms | 87.0% |

原始数据：[基线 CSV](26.3-performance-baseline.csv)、[优化 CSV](26.3-performance-optimized.csv)，以及[基线依赖](26.3-performance-baseline.profile.txt)、[优化依赖](26.3-performance-optimized.profile.txt)。CSV 的 `elapsed_ms` 是单次操作维护阶段耗时；`total` 另包括压力场景准备、修改及验证，不能当成备份与恢复耗时的简单相加。等待缩短后 `maintenance_frames` 增多是预期现象，不等于游戏 tick 推进。

10,000 区块使用实际区块序列化模板复制，修改坐标和逐块标记；包含真实存储记录，不是全部缺失的选区。恢复后逐块核对标记，并断言没有加载这些区块。模板清空了方块实体和计划刻列表，不能代表大型生电存档的 NBT 密度。已加载场景另检查方块、实体新实例和实体索引。

这是一次基线与一次优化的专用服对照，五轮平均仅用于已加载场景；未清空操作系统文件缓存，没有测量 CPU 使用率、峰值内存或做统计显著性分析。不能把表中比例推广到所有硬盘、模组配置与存档。

## 原因与改动

核对 26.3 的 `MinecraftServer.runServer`、`haveTime`、`waitUntilNextTick`、`waitForTasks` 后确认：原来的 EDB 每个维护帧仍使用普通游戏 tick 的等待期限。32 区块一批，预检、读取、写入和确认异步写完等阶段反复经过外层循环，默认每次约等 50 ms；这会形成与实际 IO 工作量无关的延迟。

现在只在正常维护阶段将两个等待期限同时锚定为当前时间加 1 ms，并继续调用原版等待方法。正常游戏、操作结束和失败暂停使用配置的 tick 间隔。连接维护另按墙钟至少间隔 50 ms，避免加速连接计数。正常游戏阶段增加的只是状态判断和时间记录；维护时主线程唤醒更频繁，不额外创建线程或扩大在途批次。

全量预检、32 条记录上限、8 ms 软预算、模拟暂停、任务屏障和写完后发布/恢复的条件均保留。watchdog 仍依据主线程的期限判断是否卡住：期限只在主线程完成一帧后更新，不由后台线程刷新。单次主线程调用仍不能被软预算抢占。

没有增加并行压缩线程池。备份仍涉及逐文件压缩与创建，消除调度空等不会消除这部分成本；若继续优化，需要先单独测量文件 IO/压缩占比，再比较有界并行或格式调整的收益。

## 回归结果

| 验证 | 结果 |
| --- | --- |
| 30 项依赖专用服，完整集成测试与压力场景 | PASS；正常停服 PASS；10 秒 watchdog 启用 |
| 纯 Fabric `build`，含 GameTest | 全部 2 个必需测试通过；正常停服检查通过 |
| C2ME + Async + Kotlin runtime，GameTest（不含 ECO） | 全部 2 个必需测试通过；正常停服 PASS |

保留世界时间和模组 tick 回调在维护期间不推进的断言，新增连接维护次数与实际经过时间的上限检查，并检查长操作中连接没有完全停摆。专用服恢复后连续 10 个游戏 tick 实测 501 ms，通过无集中补跑断言。GameTestServer 自身不按墙钟等待，因此其运行耗时不用于上表。

优化后压力 CSV 中最长维护帧为 17 ms，10,000 区块备份/恢复分别为 1/6 ms；这是 CSV 所列场景的观测值，不是全部操作或任意存档的硬上限。测试没有覆盖真实多人网络负载、10,000 个已加载高密度区块或第三方任意后台世界写入。
